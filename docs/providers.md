# Provider behavior and coverage

Verified against official documentation on 21 October 2026. Application code and provider data have separate usage rights. No provider dataset is bundled, and there is no Arkham client or scraping path.

An indexed live case initially loads one Ethereum page: from Etherscan when `ETHERSCAN_API_KEY` is set, otherwise from Blockscout. Request Arbitrum explicitly through the same expansion operation; it needs the key. Request Derive Chain (957) the same way; Etherscan has no Derive history, so it always comes from Blockscout at `explorer.derive.xyz` and needs no key. `status` lists the provider serving each chain under `providers.live.routes`. A live `historyMode: "evidence-only"` case instead begins empty with unsupported indexed-history coverage and makes no provider request; it needs no Etherscan key. Base supports targeted public RPC acquisition but is not enabled for live REST history. BSC and Optimism are also outside this REST adapter. Plan restrictions must not become false “no activity” results. Even on supported chains, an unavailable key/plan returns an explicit error.

## Shared targeted acquisition

CLI `acquire`, HTTP `POST /api/acquire` / `POST /api/investigations/:id/acquire` and MCP `flowlens_acquire` use the same bounded service. Inputs select `safe`, `bridge` or `internal`, a supported chain and an explicit wallet or known transaction. No input accepts an endpoint, credential or arbitrary RPC method. Results preserve errors, warnings, provenance and limited scope. Optional attachment merges observations into an existing live case without changing indexed transfers; demo cases reject external acquisition.

The [RPC transport](rpc-provider.md) defaults to 32 calls, 45 seconds, 2 MB per response and one request per second per chain within one process. It uses fixed endpoints and read methods, rejects redirects and has no automatic retries or alternate-provider fallback. Safe service pagination and signature budgets impose additional bounds. Independent processes do not share account/provider quota controls.

See [acquisition workflows](acquisition.md), [Safe boundaries](safe-provider.md), [known-transaction CCTP](bridge-provider.md) and [internal trace scope](trace-provider.md). Contract tests use injected responses and do not certify current live-provider availability. Specific-identifier queries disclose an investigator's selected scope to external services and require authorization; provider access does not grant data redistribution rights.

## Etherscan pagination and evidence

The adapter uses the allowlisted `https://api.etherscan.io/v2/api` endpoint. An initial `eth_blockNumber` request freezes an `endblock` boundary; `txlist` and `tokentx` are read newest-first using separate page counters, fixed page sizes, and the same frozen block range. Opaque cursors retain the chain, address, block anchor, page size and each stream's terminal state. A cursor cannot be used for another wallet/chain/page size. Cursors are validated structural state, not signed credentials.

A page contains at most ten history rows from each stream. The ERC20 history response does not supply a log index, so each distinct token transaction is hydrated with `eth_getTransactionReceipt`. Receipt transaction hash and block must match the requested history evidence; optional log hashes/blocks must agree, and removed logs are rejected. Identity mismatches fail the whole page with retryable `RECEIPT_MISMATCH`, retaining the previous cursor. Only successful receipts and actual ERC20 `Transfer` logs touching the requested wallet are normalized. Their receipt `logIndex` becomes the evidence event index; `statusRep` is token reputation and is never treated as transaction success. Duplicate receipt events across history pages deduplicate by chain/hash/kind/log index/contract. Contract-creation native value uses the created contract address when the ordinary `to` field is empty.

Amounts stay integer strings with per-contract decimals. Token symbols are provider metadata, not identity or independent verification. Different contracts and chains never share a numerical asset total. Explorer links must use the evidence chain.

The provider commits no page until all required requests have succeeded. Missing receipts, network failures and throttling produce a retryable error; the engine retains the prior committed cursor and evidence. Failed transactions are excluded. Malformed rows/logs may be omitted with a permanent coverage warning, so terminal pagination never implies every transaction was ingested. Reaching a terminal stream means only that the provider returned no further rows inside the frozen window. Newer blocks require a new investigation in this version. There is no historical refresh/reorg rollback implementation.

Each Etherscan response is capped at **2,000,000 bytes while streaming**, including when `Content-Length` is absent or incorrect. Exceeding the cap produces non-retryable `PROVIDER_RESPONSE_TOO_LARGE` and does not advance the committed history cursor. Exact duplicate normalized events deduplicate; contradictory material facts under the same stable event identity fail with `INVALID_PROVIDER_DATA` rather than silently choosing one response.

## Blockscout pagination and evidence

With no `ETHERSCAN_API_KEY`, live Ethereum history comes from Blockscout's public API v2 at the fixed `https://eth.blockscout.com/api/v2` host. Derive Chain (957) history always comes from Derive's public Blockscout explorer at the fixed `https://explorer.derive.xyz/api/v2` host, because Etherscan does not serve that chain. No key is sent or needed, but each request discloses the traced wallet to that explorer: a Derive expansion sends the wallet to `explorer.derive.xyz`. `FLOWLENS_BLOCKSCOUT=off` removes the provider for both hosts; Ethereum history then needs the Etherscan key, and a Derive expansion fails with `PROVIDER_DISABLED` (HTTP 503) before any request. Any value other than empty, `on` or `off` stops the server at startup. On Ethereum a configured key takes precedence, and coverage records name the provider that produced them (`blockscout-v2` or `etherscan-v2`); transfer `source` fields name the explorer host. Adding a key later starts separate Etherscan coverage beside the earlier Blockscout record; identical events deduplicate by canonical identity.

Three streams are read separately: `/addresses/{wallet}/transactions` (native value), `/addresses/{wallet}/token-transfers?type=ERC-20` and `/addresses/{wallet}/internal-transactions`. Blockscout lists rows newest first and paginates with an opaque `next_page_params` object. Explorers before v12, including `eth.blockscout.com` (v11.3.3 on 21 October 2026), ignore page-size requests and return 50 rows, so FlowLens fetches the provider page and keeps at most `pageSize` (1–10) rows per stream. `explorer.derive.xyz` (v12.0.3 on 23 October 2026) honours `items_count`, so FlowLens sends `items_count=pageSize` on every Derive history request; its `next_page_params` does not echo that value. Derive transaction rows carry calldata of up to about 130 KB each, so a default 50-row page can approach the response budget. The cursor stores, per stream, Blockscout's `next_page_params`, the sort position of the last consumed row and a terminal flag, plus the chain, wallet, page size and newest block of the first page. Re-reading a provider page resumes strictly after that position, so rows indexed later never shift the window. Each page is checked against Blockscout's order (block and position, block and log index, or block, transaction index and trace index); a misordered page fails without committing. `next_page_params` is provider data: only flat objects of at most 12 short keys with short alphanumeric, non-negative integer or boolean values go back, as query parameters on the same fixed path. Cursors are validated structural state bound to provider, chain, wallet and page size, not signed credentials.

Native rows require `status: "ok"`; failed transactions and zero-value calls are excluded, and contract creation credits the created contract. ERC20 rows carry Blockscout's log index, so no receipt hydration is needed; a row without decimals is omitted with a warning. Token symbols lose control and bidirectional characters and stay provider metadata, not identity: lookalike symbols occur in real histories. Blockscout names, tags, reputation and ENS fields are never imported as labels.

Blockscout's address internal-transaction list reports each frame's own success, which does not reveal a reverted parent call or transaction. Each value-moving internal row (`call`, `create`, `create2`, `selfdestruct`) is matched to its frame in `/transactions/{hash}/raw-trace`, one read per distinct transaction on the page. `eth.blockscout.com` returns that trace as a flat Parity-style frame list; `explorer.derive.xyz` returns a nested Geth `callTracer` tree. FlowLens walks the tree in pre-order, which is the order of Blockscout's internal-transaction `index`, and derives each frame's trace address from its position. Sender, recipient and value must agree, or the page fails with retryable `TRACE_MISMATCH`; an empty trace raises retryable `TRACE_UNAVAILABLE`, which holds back only the internal stream, as described below. Frames under a reverted ancestor or transaction are excluded with a warning. The frame's trace address becomes the event index (`trace.0.1`), the identity the transaction-scoped `callTracer` acquisition also uses. Delegate, static and callcode frames are skipped as non-moving, and the transaction's own call (trace index 0) stays with the native stream. A trace above the response budget or 5,000 frames omits that transaction's internal rows with a permanent warning instead of blocking the stream. Derive's internal list includes zero-value and static calls (its pagination carries `include_zero_value: true`), so a 10-row page may hold few value transfers.

Derive Chain subaccounts are NFT-style tokens, which this adapter does not read, and their collateral, positions and trades are records inside Derive's contracts. A Derive trace therefore shows deposits, withdrawals and other native, ERC20 and internal transfers that touch the address, not subaccount balances or trading; every Derive page carries a warning saying so.

The internal stream is Blockscout's slowest endpoint and can fail on its own; on 23 October 2026 it stopped answering while the other two kept working. When only the internal stream is unavailable (`NETWORK_ERROR`, `PROVIDER_HTTP_ERROR`, `RATE_LIMITED` or `TRACE_UNAVAILABLE`) and another stream still has rows to read, the page commits its native and ERC20 rows, reports streams `native` and `erc20` with a warning, and leaves the internal cursor where it was, so the next page asks again. A stream that starts after the first page stays inside the first page's window: rows above its newest block are skipped. If the internal stream is the only one left, the error stands and nothing is committed. Integrity failures such as `TRACE_MISMATCH` still fail the whole page.

Each Blockscout response is capped at **4,000,000 bytes while streaming**, because pre-v12 pages carry 50 full rows including calldata. Exceeding the cap on a history page fails it with non-retryable `PROVIDER_RESPONSE_TOO_LARGE`. HTTP 429 is retryable `RATE_LIMITED`. HTTP 401 or 403, including a Cloudflare browser check, is `ACCESS_DENIED` and not evidence of no activity. 422 is `PROVIDER_ERROR`; 404 (indexing lag) and 5xx are retryable `PROVIDER_HTTP_ERROR`. Redirects are refused. Nothing retries automatically, and the previous cursor stays committed.

## Budgets and rate limits

The Etherscan provider shares a queue paced at one request per second. A first page makes at most 13 requests (block anchor, two history streams, up to ten receipts); later pages make at most 12. An expansion is explicitly bounded to one wallet, at most three pages and 80 total graph nodes. The engine rejects an over-budget page atomically. Receipt parsing is bounded to 2,000 logs per receipt. There are no automatic recursive requests or network retries.

Etherscan documents a free limit of three calls/second, 100,000/day on selected chains. Our pacing is deliberately lower. Account-level quota is external: other clients may consume it. Separate CLI processes have separate pacing queues; do not run concurrent live CLI jobs against the same key. CLI/API writers share a per-file lock for state safety, but that lock is not an account-level rate limiter. Provider throttles and access denials remain explicit. No service or paid tier is purchased automatically.

The Blockscout provider has its own queue paced at one request every 500 ms, shared by both hosts. A page makes at most 3 + `pageSize` requests: three history reads and one trace per distinct transaction behind an internal transfer. On 21 October 2026 `eth.blockscout.com`, and on 23 October 2026 `explorer.derive.xyz`, advertised `x-ratelimit-limit: 180` per minute for keyless v2 requests; Blockscout's documentation gives 300 per minute per IP as the keyless default. Its Etherscan-compatible `/api` advertised 10 requests per window of more than half an hour, so FlowLens does not use it. The limit is per IP: other software on the same network shares it, and separate processes pace independently.

Blockscout's documentation announces that per-instance APIs such as `eth.blockscout.com/api/v2` will be deprecated in favour of its keyed PRO API (dated only "July 1" on 21 October 2026). Keyless access may stop; the adapter then reports `ACCESS_DENIED` or an HTTP error, never empty history. No terms specific to the free per-instance API were found; Blockscout's separate paid Data API terms limit data to internal use. FlowLens bundles no Blockscout data and its fixtures are synthetic. Treat returned data as material for your own investigation; redistribution rights remain unverified.

## Local storage and errors

The HTTP API binds only to `127.0.0.1`. It accepts loopback hosts/origins and JSON mutation bodies, rejects oversized input, and exposes no CORS grant. Server cases are `.local/cases/<id>.json`, stored via an atomic rename with private file modes. The CLI can instead use a user-chosen local path. Both use the same exclusive lock file and engine. A crash may leave `<case>.json.lock`; after verifying no writer is active, remove that exact stale lock before retrying.

A full snapshot PUT includes its original `updatedAt` timestamp. The server checks it against current storage and returns HTTP 409 `CASE_CONFLICT` for stale state; on success use the returned snapshot and new timestamp. Do not manufacture a new timestamp before saving. Expansion operations serialize and reread the latest committed case. A shared-file lock conflict returns HTTP 409 `CASE_BUSY`.

JSON errors use `{ "error": { "code": "...", "message": "...", "retryable": false } }`. Successful expansion responses may still contain `coverage[].status = "error"`, with validated `errorCode` and `retryable` fields; inspect coverage instead of treating HTTP 200 or process exit 0 as proof of full history. A successful retry clears the prior error fields. CLI create/expand exits 2 after saving a case with coverage errors; the JSON result remains on stdout. Validation/unavailable-key failures exit 1 with a JSON error on stderr.

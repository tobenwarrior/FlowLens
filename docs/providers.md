The routes below describe implemented provider capabilities and configured routing, not endpoint health or a guarantee of live coverage. Checked against the current implementation on 31 October 2026. Application code and provider data have separate usage rights. No provider dataset is bundled, and there is no Arkham client or scraping path.

An indexed live case initially loads one Ethereum page: Etherscan takes precedence when `ETHERSCAN_API_KEY` is set; otherwise the keyless legacy Blockscout route serves Ethereum. Derive Chain (957) always uses its keyless legacy Blockscout explorer. On Base (8453), a configured self-hosted endpoint selects first, then `ALCHEMY_API_KEY`, then a permitted `BLOCKSCOUT_API_KEY` for unified hosted Blockscout. On Arbitrum (42161), Etherscan takes precedence when `ETHERSCAN_API_KEY` is set; otherwise a permitted `BLOCKSCOUT_API_KEY` selects unified Blockscout. Robinhood Chain (4663) is served only by a permitted `BLOCKSCOUT_API_KEY` through unified Blockscout when explicitly expanded; it has no keyless history route. A configured route is a capability, not a health check or complete-history guarantee; `status` only names it under `providers.live.routes`. `FLOWLENS_BLOCKSCOUT=off` disables every Blockscout route, including self-hosted Base and keyed Robinhood, but does not disable an independently configured Alchemy Base route. A live `historyMode: "evidence-only"` case begins empty, makes no provider request and needs no key. HypurrTrace serves HyperEVM (999) when enabled. BSC and Optimism are outside this history adapter. Base also remains available for targeted public-RPC protocol acquisition, which is separate from indexed history.

## Shared targeted acquisition

CLI `acquire`, HTTP `POST /api/acquire` / `POST /api/investigations/:id/acquire` and MCP `flowlens_acquire` use the same bounded service. Inputs select `safe`, `bridge` or `internal`, a supported chain and an explicit wallet or known transaction. No input accepts an endpoint, credential or arbitrary RPC method. Results preserve errors, warnings, provenance and limited scope. Optional attachment merges observations into an existing live case without changing indexed transfers; demo cases reject external acquisition.

The [RPC transport](rpc-provider.md) defaults to 32 calls, 45 seconds, 2 MB per response and one request per second per chain within one process. It uses fixed endpoints and read methods, rejects redirects and has no automatic retries or alternate-provider fallback. Safe service pagination and signature budgets impose additional bounds. Independent processes do not share account/provider quota controls.

See [acquisition workflows](acquisition.md), [Safe boundaries](safe-provider.md), [known-transaction CCTP](bridge-provider.md) and [internal trace scope](trace-provider.md). Contract tests use injected responses and do not certify current live-provider availability. Specific-identifier queries disclose an investigator's selected scope to external services and require authorization; provider access does not grant data redistribution rights.

## Etherscan pagination and evidence

The adapter uses the allowlisted `https://api.etherscan.io/v2/api` endpoint. An initial `eth_blockNumber` request freezes an `endblock` boundary; `txlist` and `tokentx` are read newest-first using separate page counters, fixed page sizes, and the same frozen block range. Opaque cursors retain the chain, address, block anchor, page size and each stream's terminal state. A cursor cannot be used for another wallet/chain/page size. Cursors are validated structural state, not signed credentials.

A page contains at most ten history rows from each stream. The ERC20 history response does not supply a log index, so each distinct token transaction is hydrated with `eth_getTransactionReceipt`. Receipt transaction hash and block must match the requested history evidence; optional log hashes/blocks must agree, and removed logs are rejected. Identity mismatches fail the whole page with retryable `RECEIPT_MISMATCH`, retaining the previous cursor. Only successful receipts and actual ERC20 `Transfer` logs touching the requested wallet are normalized. Their receipt `logIndex` becomes the evidence event index; `statusRep` is token reputation and is never treated as transaction success. Duplicate receipt events across history pages deduplicate by chain/hash/kind/log index/contract. Contract-creation native value uses the created contract address when the ordinary `to` field is empty.

Amounts stay integer strings with per-contract decimals. Token symbols are provider metadata, not identity or independent verification. Different contracts and chains never share a numerical asset total. Explorer links must use the evidence chain.

The provider commits no page until all required requests have succeeded. Missing receipts, network failures and throttling produce a retryable error; the engine retains the prior committed cursor and evidence. Failed transactions are excluded. Malformed rows/logs may be omitted with a permanent coverage warning, so terminal pagination never implies every transaction was ingested. Reaching a terminal stream means only that the provider returned no further rows inside the frozen window. Newer blocks require a new investigation in this version. There is no historical refresh/reorg rollback implementation.

Each Etherscan response is capped at **2,000,000 bytes while streaming**, including when `Content-Length` is absent or incorrect. Exceeding the cap produces non-retryable `PROVIDER_RESPONSE_TOO_LARGE` and does not advance the committed history cursor. Exact duplicate normalized events deduplicate; contradictory material facts under the same stable event identity fail with `INVALID_PROVIDER_DATA` rather than silently choosing one response.

## Alchemy Transfers pagination and evidence

When no self-hosted Base endpoint is configured and `ALCHEMY_API_KEY` is present, Base (8453) uses provider ID `alchemy-transfers` before keyed Blockscout. The adapter calls Alchemy's fixed Base Transfers endpoint and sends no request when the key is absent. A free account may be accepted, but quotas and plan access are controlled by Alchemy; this repository has no live Alchemy key, so offline adapter tests do not certify endpoint access or coverage.

Each page queries `alchemy_getAssetTransfers` for six directional streams: native, ERC-20 and internal categories, each `from` and `to` the requested wallet. The first request freezes an `eth_blockNumber` fence. Local `pageSize` is 1–10 per direction; provider pages are capped at 1,000 rows. Alchemy's short-lived page key (about ten minutes) is never persisted: the durable cursor stores the frozen block boundary and consumed event identities, then re-queries the provider at that boundary. If a saturated page contains only already-consumed identities, the stream stops with `PAGINATION_LIMIT` rather than skipping rows. The shared cursor ceiling is 4,096 characters; unusually large same-block bursts can also reach that explicit limit and leave partial coverage.

Native rows require a successful receipt. ERC-20 rows are matched to the receipt's canonical `Transfer` log and log index. Internal rows require a successful receipt and exactly one matching successful frame in the provider's full `callTracer` tree. Canonical hash/block/log/frame identities are retained; contradictory or mismatched material facts fail the page. A response is bounded to 4,000,000 bytes and 15 seconds. If internal calls fail after direct rows were collected, native and ERC-20 evidence is retained while the internal cursor remains unchanged for an explicit resume. NFTs, gas fees, bridge matches and labels are outside this adapter.

## Blockscout pagination and evidence

The legacy keyless routes use `https://eth.blockscout.com/api/v2` for Ethereum and `https://explorer.derive.xyz/api/v2` for Derive Chain (957). Each request discloses the traced wallet to that explorer. A user-supplied `BLOCKSCOUT_API_KEY` selects the unified API at `https://api.blockscout.com/{chainId}/api/v2` for configured Base, Arbitrum and Robinhood Chain routes; the key is sent as a bearer credential and is required even on the free tier. Hosted chain access is account-plan specific: a request from one free-tier account returned HTTP 402 on 31 October 2026 and its response requested Builder, Business or Pro access; paid-tier eligibility was not tested. Arbitrum and Robinhood access is configured by the key and remains provider- and case-scoped; a terminal page does not establish complete history. `FLOWLENS_BLOCKSCOUT=off` removes all legacy, self-hosted and keyed Blockscout routes before any request. Any value other than empty, `on` or `off` stops the server at startup. Etherscan takes precedence for Ethereum or Arbitrum when `ETHERSCAN_API_KEY` is set. Coverage records identify the provider (`blockscout-v2`, `blockscout-pro-v2`, `blockscout-self-hosted-v1-<endpoint-digest>` or `etherscan-v2`); transfer `source` fields retain the selected host. Provider selection is not fallback: an access or plan error remains visible.

Three streams are read separately: `/addresses/{wallet}/transactions` (native value), `/addresses/{wallet}/token-transfers?type=ERC-20` and `/addresses/{wallet}/internal-transactions`. Blockscout lists rows newest first and paginates with an opaque `next_page_params` object. Legacy explorers that ignore page-size requests may return 50 rows, so FlowLens keeps at most `pageSize` (1–10) rows per stream; the keyed unified route also accepts the same 1–10 local bound. The Derive explorer honours `items_count`, while its `next_page_params` does not echo that value. Derive transaction rows can carry large calldata, so a provider page can approach the response budget. The cursor stores, per stream, Blockscout's `next_page_params`, the sort position of the last consumed row and a terminal flag, plus the chain, wallet, page size and newest block of the first page. Re-reading a provider page resumes strictly after that position, so rows indexed later never shift the window. Each page is checked against Blockscout's order (block and position, block and log index, or block, transaction index and trace index); a misordered page fails without committing. `next_page_params` is provider data: only flat objects of at most 12 short keys with short alphanumeric, non-negative integer or boolean values go back, as query parameters on the same fixed path. Cursors are validated structural state bound to provider, chain, wallet and page size, not signed credentials.

Native rows require `status: "ok"`; failed transactions and zero-value calls are excluded, and contract creation credits the created contract. ERC20 rows carry Blockscout's log index, so no receipt hydration is needed; a row without decimals is omitted with a warning. Token symbols lose control and bidirectional characters and stay provider metadata, not identity: lookalike symbols occur in real histories. Blockscout names, tags, reputation and ENS fields are never imported as labels.

Blockscout's address internal-transaction list reports each frame's own success, which does not reveal a reverted parent call or transaction. Each value-moving internal row (`call`, `create`, `create2`, `selfdestruct`) is matched to its frame in `/transactions/{hash}/raw-trace`, one read per distinct transaction on the page. `eth.blockscout.com` returns that trace as a flat Parity-style frame list; `explorer.derive.xyz` returns a nested Geth `callTracer` tree. FlowLens walks the tree in pre-order, which is the order of Blockscout's internal-transaction `index`, and derives each frame's trace address from its position. Sender, recipient and value must agree, or the page fails with retryable `TRACE_MISMATCH`; an empty trace raises retryable `TRACE_UNAVAILABLE`, which holds back only the internal stream, as described below. Frames under a reverted ancestor or transaction are excluded with a warning. The frame's trace address becomes the event index (`trace.0.1`), the identity the transaction-scoped `callTracer` acquisition also uses. Delegate, static and callcode frames are skipped as non-moving, and the transaction's own call (trace index 0) stays with the native stream. A trace above the response budget or 5,000 frames omits that transaction's internal rows with a permanent warning instead of blocking the stream. Derive's internal list includes zero-value and static calls (its pagination carries `include_zero_value: true`), so a 10-row page may hold few value transfers.

Derive Chain subaccounts are NFT-style tokens, which this adapter does not read, and their collateral, positions and trades are records inside Derive's contracts. A Derive trace therefore shows deposits, withdrawals and other native, ERC20 and internal transfers that touch the address, not subaccount balances or trading; every Derive page carries a warning saying so.

The internal stream is Blockscout's slowest endpoint and can fail on its own. When only the internal stream is unavailable (`NETWORK_ERROR`, `PROVIDER_HTTP_ERROR`, `RATE_LIMITED` or `TRACE_UNAVAILABLE`) and another stream still has rows to read, the page commits its native and ERC20 rows, reports streams `native` and `erc20` with a warning, and leaves the internal cursor where it was, so the next page asks again. A stream that starts after the first page stays inside the first page's window: rows above its newest block are skipped. If the internal stream is the only one left, the error stands and nothing is committed. Integrity failures such as `TRACE_MISMATCH` still fail the whole page.

Each Blockscout response is capped at **4,000,000 bytes while streaming**, because pre-v12 pages carry 50 full rows including calldata. Exceeding the cap on a history page fails it with non-retryable `PROVIDER_RESPONSE_TOO_LARGE`. HTTP 429 is retryable `RATE_LIMITED`. HTTP 401 or 403, including a Cloudflare browser check, is `ACCESS_DENIED` and not evidence of no activity. 422 is `PROVIDER_ERROR`; 404 (indexing lag) and 5xx are retryable `PROVIDER_HTTP_ERROR`. Redirects are refused. Nothing retries automatically, and the previous cursor stays committed.

## HypurrTrace indexed history

When `FLOWLENS_HYPURRTRACE` is empty or `on`, chain 999 uses the keyless `https://trace.hypurrscan.io/api/v1` service with provider ID `hypurrtrace-indexed`. A page defaults to 10 rows per stream and accepts up to 100. Successful native HYPE rows are checked by transaction status. ERC-20 rows come from the indexed `Transfer`-log stream without per-transaction hydration. Internal value calls are retained only when the provider's published full call tree confirms the frame path and successful ancestors. NFTs, gas fees, labels and independent RPC verification are outside this adapter.

The first page freezes the provider's index status. Cursors retain that index fence and separate offsets for native, ERC-20 and internal streams; activity indexed after the fence is not silently folded into the case. The adapter stops at the provider's 10,000-row bound with explicit partial coverage rather than claiming exhaustion. `FLOWLENS_HYPURRTRACE=off` disables chain 999 and returns `PROVIDER_DISABLED`.

## HyperCore ledger evidence

The standalone HyperCore operation reads Hyperliquid's public-info `userNonFundingLedgerUpdates` request for one EVM account and time window. It accepts one page of at most 500 entries and exposes a durable inclusive cursor for the next page. Only non-funding ledger updates are imported: funding payments and trade fills remain outside scope. Coverage records `retention: "undocumented"`, and even an exhausted provider window has `fullHistory: false`.

Without a case ID, the caller receives a read-only provider result. With a live case ID, the page is persisted under `protocolEvidence.hypercore` and resumed inside that case's frozen window; it does not change EVM chain-999 transfers, graph nodes or gross/net totals. This is a separate provider window, not an ownership or complete-accounting claim.

`flow.endpointKind` distinguishes `wallet-transfer`, `protocol-accounting`, `bridge-accounting` and `unknown`. `flow.accountingDirection` is separate from wallet endpoint direction: a recognized `borrowLend` supply is accounting out and a withdrawal is accounting in, while its wallet endpoints remain null. A protocol-accounting endpoint is not an undiscovered wallet address. Unknown operations retain unknown direction.

The human ledger can relate a deposit or withdrawal to an already loaded Arbitrum Bridge2 USDC transfer. The shared domain helper requires an exact hash, chain 42161, canonical USDC contract, six decimals, exact raw amount, successful ERC-20 status, the account/Bridge2 endpoints in the correct direction, and a unique matching event. It does not fetch another chain automatically or join on rounded values or time alone. Related Arbitrum addresses remain chain-qualified evidence; they are not copied into HyperCore endpoints, added to EVM totals again, or described as bridge finalization proof.

## Self-hosting Blockscout

The optional Base connector reads `FLOWLENS_BASE_BLOCKSCOUT_URL` only from the FlowLens server environment. It accepts a bare `http://` or `https://` origin on `127.0.0.1` or `[::1]`; paths, query strings, fragments and credentials are rejected. A remote indexer must remain bound to its remote loopback and be reached through an SSH tunnel, for example `ssh -N -L 4010:127.0.0.1:4010 user@archive-host`; FlowLens still uses `http://127.0.0.1:4010`. HTTP/API and MCP callers cannot supply or override the URL.

No Blockscout API key is needed for this route, and no key is sent to it. When `FLOWLENS_BLOCKSCOUT` is not `off`, self-hosted Base is selected before Alchemy and hosted keyed Blockscout. `FLOWLENS_BLOCKSCOUT=off` disables this route too. The existing hosted routes and key behavior are unchanged.

Before every self-hosted wallet-history page, FlowLens checks `POST /api/eth-rpc` with `eth_chainId` and requires Base chain ID `0x2105` (8453), then checks `GET /api/v2/main-page/indexing-status`. Both `finished_indexing` and `finished_indexing_blocks` must be `true`, and both `indexed_blocks_ratio` and `indexed_internal_transactions_ratio` must be `1.0`. A missing or incomplete value, including `null`, produces `SELF_HOSTED_NOT_READY`; a different chain ID produces `SELF_HOSTED_CHAIN_MISMATCH`. The readiness requests are bounded by the same 4,000,000-byte response cap and 15-second timeout; redirects, automatic retries and provider fallback are refused. A readiness pass is not a genesis proof: the API cannot establish that `FIRST_BLOCK=0` and `TRACE_FIRST_BLOCK=0` were used or that archive RPC history is complete. Each page carries this caveat, and the provider ID/cursor is bound to the endpoint with the `blockscout-self-hosted-v1-` prefix.

The [self-hosted Base deployment guide](self-hosted-base.md) is a preparation packet only. It documents the future host's archive-RPC, storage and deployment requirements; this repository does not run a Base indexer or claim live real-index coverage. Review endpoint and data-use rights before connecting an operator instance.

## Budgets and rate limits

The Etherscan provider shares a queue paced at one request per second. A first page makes at most 13 requests (block anchor, two history streams, up to ten receipts); later pages make at most 12. An expansion is explicitly bounded to one wallet, at most three pages and 2,000 retained nodes; the human graph projection separately shows at most 80 counterparties plus the focus wallet. The engine rejects an over-budget page atomically. Receipt parsing is bounded to 2,000 logs per receipt. There are no automatic recursive requests or network retries.

Etherscan documents a free limit of three calls/second, 100,000/day on selected chains. Our pacing is deliberately lower. Account-level quota is external: other clients may consume it. Separate CLI processes have separate pacing queues; do not run concurrent live CLI jobs against the same key. CLI/API writers share a per-file lock for state safety, but that lock is not an account-level rate limiter. Provider throttles and access denials remain explicit. No service or paid tier is purchased automatically.

Each Blockscout provider instance queues requests at one request every 500 ms. The legacy Ethereum/Derive routes share one instance; keyed Base/Arbitrum/Robinhood routes share another. A page makes at most 3 + `pageSize` requests: three history reads and one trace per distinct transaction behind an internal transfer. Keyless legacy limits are per IP; keyed unified limits and allowed chains are account-plan specific. Other software on the same network or account can consume quota, and separate processes pace independently. FlowLens does not purchase a plan, retry automatically or switch endpoints after an access error.

Keyless per-instance routes may be deprecated or restricted in favour of the unified API. If a hosted route denies access, the adapter reports `ACCESS_DENIED` or an HTTP error, never empty history. A free-tier key is still a key and does not guarantee Base or any other chain. FlowLens bundles no Blockscout data and its fixtures are synthetic. Treat returned data as material for your own investigation; redistribution rights remain unverified.

## Local storage and errors

The HTTP API binds only to `127.0.0.1`. It accepts loopback hosts/origins and JSON mutation bodies, rejects oversized input, and exposes no CORS grant. Server cases are `.local/cases/<id>.json`, stored via an atomic rename with private file modes. The parsed snapshot is capped at 5 MB, 20,000 transfers and 2,000 retained nodes; full loaded transfer/address evidence remains available within those bounds even though the human graph projection shows at most 80 counterparties plus the focus wallet. The CLI can instead use a user-chosen local path. Both use the same exclusive lock file and engine. A crash may leave `<case>.json.lock`; after verifying no writer is active, remove that exact stale lock before retrying.

A full snapshot PUT includes its original `updatedAt` timestamp. The server checks it against current storage and returns HTTP 409 `CASE_CONFLICT` for stale state; on success use the returned snapshot and new timestamp. Do not manufacture a new timestamp before saving. Expansion operations serialize and reread the latest committed case. A shared-file lock conflict returns HTTP 409 `CASE_BUSY`.

JSON errors use `{ "error": { "code": "...", "message": "...", "retryable": false } }`. Successful expansion responses may still contain `coverage[].status = "error"`, with validated `errorCode` and `retryable` fields; inspect coverage instead of treating HTTP 200 or process exit 0 as proof of full history. A successful retry clears the prior error fields. CLI create/expand exits 2 after saving a case with coverage errors; the JSON result remains on stdout. Validation/unavailable-key failures exit 1 with a JSON error on stderr.
